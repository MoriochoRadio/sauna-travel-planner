## 2. v1 결정: 소스 A (직접 큐레이션)

선택 근거:
1. **즉시 동작** — 외부 의존성 없이 앱을 바로 만들고 검증 가능
2. **법적 안전** — 크롤링 ToS 리스크 회피
3. **LLM 근거 품질** — 큐레이터가 검증한 장소만 추천에 사용 → 환각(없는 장소) 억제
4. **비용 0** — 무료 플랜 일관성 유지

단점(신선도)은 운영 단계에서 소스 B(tourAPI)를 정기 동기화하는 GitHub Actions 워크플로우로 보완 예정.

## 3. 데이터 모델 매핑 (소스 → 스키마)

- `Place`(schema.ts): 장소 1건 = 사우나/찜질방/온천(restaurant/attraction 포함)
- `Region`(schema.ts): 지역 단위 묶음, region별 `places[]` 보유
- 추천 시 LLM에는 **해당 region의 places JSON만** 직렬화 전달(토큰 절약 + 환각 억제)

## 4. 후속 단계 데이터 보강 계획 (로드맵)

| 단계 | 소스 | 방식 |
|------|------|------|
| v1.1 | tourAPI | GitHub Actions 주기 크론 → seed 보강 PR 자동 생성 |
| v1.2 | OSM Overpass | 온천/찜질방 POI 좌표 보강(지도 시각화 대비) |
| v2 | 리뷰 집계 | 공식 파트너 API 또는 운영자 승인 범위 내만 |

## 5. 데이터 품질 기준

- 각 region: 사우나계(sauna/jjimjilbang/spa) ≥ 3, restaurant ≥ 3, attraction ≥ 2 (검증 테스트 Task 1-2)
- 모든 장소: `name`, `summary`, `highlights`(≥1) 필수
- `priceLevel`/`avgDurationMin`은 추천 타임라인 배치의 핵심 변수 → 누락 금지
